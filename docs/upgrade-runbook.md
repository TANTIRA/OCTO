# Upgrade runbook — self-hosted Supabase and the OCTO app stack

How to move a pinned release forward, and how to get back if it goes wrong. Owner: Platform / DevOps. **T2** ([AGENTS.md](../AGENTS.md)) — an upgrade touches auth, financial data, and infrastructure.

This is the "upgrade and rollback rehearsed on staging" half of ADR-0002's production acceptance list. The procedure is here; the rehearsal is what makes it real. `deploy/drill/rollback-rehearsal.sh` exercises the rollback path locally so the procedure is known to work before it is needed — a local run is preparation, never acceptance.

## 1. What actually gets upgraded

Two things move independently, and conflating them is the common mistake:

| Layer | What it is | How it moves |
| --- | --- | --- |
| Supabase services | The live **Dokploy Supabase template** — raw `composeFile` + generated env, Kong gateway, `octo-supabase-*` containers (`infra/supabase/README.md`, "Deployed vs vendored") | Bump image tags + digests in the Dokploy compose file, review the changelog, redeploy, then restart the app project |
| Schema | Flyway migrations in `db/migrations/`, applied at api boot | Merge a migration; it applies on the next api boot. Forward-only — see §5 |
| App stack | `octo-api`, `octo-web`, `octo-agents` built from this repo | Redeploy a new commit; image tags carry the commit sha (`deploy/README.md`, "Environment model") |
| Vendored reference | `infra/supabase/vendor/` at `self-hosted/v0.8.1` (`vendor/.supabase-version`) | `vendor/update.sh` three-way merge, or copy `docker/` over `vendor/` and review the diff. **This does not touch the deployed stack** |

`vendor/update.sh` does not upgrade production. Updating the deployed service means bumping tags in Dokploy.

## 2. Preconditions

- [ ] Target environment is **staging**, isolated from production data (ADR-0002 §Environment topology). An upgrade rehearsed first on staging is the requirement; production is not the rehearsal.
- [ ] A verified base backup exists and WAL archiving is continuous — see [restore-runbook.md](restore-runbook.md) §3. **A backup you have not restored is not a verified backup.**
- [ ] The release notes and security advisories for every new tag have been read (`vendor/CHANGELOG.md`, upstream release notes).
- [ ] Every new image is pinned by immutable tag **and** digest, and scanned before deployment (`infra/README.md` guardrails).
- [ ] Current tags and digests are recorded in the drill record ([drill-evidence-template.md](drill-evidence-template.md)) — you cannot roll back to a version you did not write down.
- [ ] The previous rehearsal's open follow-ups are closed or explicitly accepted.

## 3. Upgrade procedure

1. **Rehearse the rollback path first.** Run `deploy/drill/rollback-rehearsal.sh` — it proves the base backup plus WAL restore returns the schema to the pre-upgrade state, and measures how long that takes.
2. **Record the rollback point:** base backup taken, WAL archived past it, and the recovery target time. Without this there is no rollback, only hope.
3. **Apply the upgrade in the lowest environment that can show the failure** — staging before production.
4. **Watch the boot window.** The api applies Flyway at startup and the healthcheck has a 90 s `start_period` (`deploy/dokploy.compose.yml`). Plain `CREATE INDEX` migrations (e.g. V38) take `SHARE` locks that block writes while they build and can outlast that window on a large table — schedule releases carrying them for a low-traffic window (`deploy/README.md`, "Verify after deploy").
5. **Verify:**
   ```bash
   curl -sf https://api-octo.mesta.click/actuator/health            # {"status":"UP"}
   curl -sf https://api-octo.mesta.click/actuator/health/readiness   # includes db
   curl -sf -o /dev/null -w '%{http_code}\n' https://octo.mesta.click/app
   ```
   Then confirm `octo.flyway_schema_history` has no `success = false` row and `installed_by` is `octo_migrate`.
6. **Env changes do not recreate containers.** `docker compose up -d` only recreates services whose rendered config changed, so a Supabase-side key or env change leaves the api running against a stale JWKS cache. Restart the app project (`VPS_restartProjectV1`) after rotating signing material (`deploy/README.md`, "Gotchas").
7. **Record the result** on [drill-evidence-template.md](drill-evidence-template.md), including measured timings and any deviation.

## 4. Key material

Rotating `JWT_KEYS`/`JWT_JWKS` is an upgrade of its own and the riskiest one, because a mistake locks every user out at once (see [incident-runbook.md](incident-runbook.md) §5.5):

- ES256 key material cannot be generated by the Dokploy helpers — use `utils/add-new-auth-keys.sh` from `infra/supabase/vendor/` with the deployment's `JWT_SECRET`.
- `{"keys":[]}` from `/auth/v1/.well-known/jwks.json` means GoTrue has no asymmetric material and the api's JWKS decoder will reject every token.
- `AUTH_JWKS_URL` must be the **internal** Kong path, not the public URL: the api container cannot hairpin back out through Traefik.
- Never blank `AUTH_ISSUER`/`AUTH_AUDIENCE` to work around a 401 — with them blank, issuer/audience validation is skipped and any JWKS-signed token authenticates.

## 5. Rollback

The stack is stateless and **migrations are forward-only** (`deploy/README.md`, "Rollback"; `WHITEPAPER.md` §11): applied migrations are never reverted, edited, or deleted. Two different situations need two different answers:

| Situation | Rollback |
| --- | --- |
| Code is bad, schema is fine | Redeploy the previous branch commit from Dokploy. Image tags carry the commit sha, so the previous running image is nameable and liftable. |
| A migration must be undone | **There is no down-migration.** Restore the pre-upgrade state from base backup + WAL to the pre-migration time, then roll the code back to match. Grant the restore its own RTO budget. |

For the second case, follow [restore-runbook.md](restore-runbook.md) §4 for the point-in-time restore and §7 for the post-restore checklist. `deploy/drill/rollback-rehearsal.sh` is the executable form of this path: it migrates to V(n-1), backs up, applies V(n), then restores to the pre-upgrade point and asserts the function fingerprint, row counts, and audit chain all match the pre-upgrade state.

**Do not** hand-edit `flyway_schema_history` to make a failed migration disappear. A history row written by anything other than the migration identity is an integrity problem — escalate it ([incident-runbook.md](incident-runbook.md) §5.2).

## 6. Rehearsal cadence

Quarterly, and before any upgrade that changes schema, auth, or storage. Each rehearsal is logged on [drill-evidence-template.md](drill-evidence-template.md). `deploy/README.md` ("Rollback") notes that every PR states a rollback path and *none has been rehearsed*; this runbook plus the harness is how that changes.

## 7. What this does not cover

- The restore procedure itself — [restore-runbook.md](restore-runbook.md) owns it.
- The live Supabase template's own upgrade mechanics beyond bumping tags and redeploying; upstream owns the compose distribution.
- Neo4j and TypeDB, which have their own ADRs (0004, 0003) and their own pending upgrade runbooks.
- Postgres major-version moves (e.g. `docker-compose.pg17.yml`, `utils/upgrade-pg17.sh` in the vendored tree), which are a different procedure from a tag bump and would need their own rehearsal.
